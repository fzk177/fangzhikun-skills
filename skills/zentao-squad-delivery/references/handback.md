# 交回用户与回复唤醒

任务、Bug 两条分支的全部异常、来源／ID 缺失或冲突、依赖缺失和需要用户回答的出口共用此约定。不得因已提交或已写入一部分就继续下一阶段，也不能用唤醒自动重试部分成功的操作。

1. 只读核对真实进度，区分「未执行／已成功／未能确认」。仅回读必要对象，不重试写入，不自动回滚。记录已导入文件、本地提交、本地资料、禅道状态与备注／指派的实际结果。
2. 用 `multica workspace member list --output json` 核实当前工作区成员 fangzk。使用返回的成员用户 UUID 指派，不拿邮箱、成员记录 ID 或触发者字段冒充用户 UUID；同时核验本轮万事屋 agent ID。无法唯一核验则停止该项写入并如实报告。
3. 将 issue 指派回该成员并置 `blocked`。因用户要求的人工审阅而交回时使用 `in_review`；这不适用于已经授权的正常自动链路。
4. 指派后立即为本 issue 登记只匹配该成员评论的唤醒。以下命令所有占位值都须取自本轮核验事实：

```text
multica issue wakeup create <issue-id>
  --event comment.created
  --filter-actor-type member --filter-actor-id <fangzk的用户UUID>
  --agent-id <万事屋agent UUID> --expires-in 168h
```

登记前先 `multica issue wakeup list <issue-id> --output json`：同 issue 已有启用、未过期且 actor、agent、事件、回复线程一致的规则时复用，不重复创建。失效或已触发的一次性规则不算有效等待。若本轮应在线程回复，创建时携带本轮 `--parent <comment-id>`；唤醒指令要求先读 fangzk 本人新评论，判断确认、修改意见或提问，再按已有真实结果决定可继续的范围。只接受该成员本人明确确认，不将超时、智能体评论或问询当作授权。

5. 本轮只发一条最终评论：简述停止原因、真实状态、需要用户回答的事项，以及唤醒登记／复用结果。末尾写「直接回复本 issue 即可继续」。指派、状态或唤醒登记失败也必须如实说明，不能声称已安排成功；无法保证唤醒时请用户回复后手动指派回万事屋。

唤醒后重新读取 issue、扫描评论摘要并展开相关线程，判断成员是否解答了缺口。只有本 Skill 为交回用户登记的规则唤醒，且该成员明确补齐缺口／确认继续、入口其余证据仍有效时，才可把 issue 从该成员重新指派给万事屋、置 `in_progress` 并继续尚未发生的已授权步骤；这属于原交付的续接，不要求成员再手动改指派。成员仅提问时先回答，不能当成确认。ID 冲突须由成员明确裁定对象类型与唯一 ID 并撤销冲突旧值；普通新提及不能自行覆盖历史候选。

只要上轮有禅道写入尝试、回读不确定或部分成功，就仅报告回读和待处理项，不自动重复解决、完成、指派或新增备注，也不为继续而删除本地尝试标记。一次性规则消耗后如再次交回用户，重新登记一次有效等待。
