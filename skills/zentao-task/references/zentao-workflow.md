# 禅道写入工作流

仅在阶段六或七读取本文件。任何写操作都必须使用最近一次尚未处理的完整预览和计划哈希。

## 阶段六：受控完成任务

仅在本次代码已按 Git 核对阶段完成提交后，使用已持久化的最终实际时间和基于实际交付事实整理的交付备注生成预览，不传 `--apply`。同一条备注必须分别新增到任务本身和任务 `storyId` 所指向的归属需求下，不能改写任务或需求正文。

备注固定使用以下结构，四个分段都必须保留：

```text
涉及模块：
- <仓库、服务、业务模块、接口、页面、配置或数据处理范围>

主要调整：
- <本次实际完成的代码或配置调整及其结果>

验收口径：
- <可验证的功能场景、边界条件、数据结果或上下游联动结果>

其他影响：
- <兼容性、接口、数据、数据库、配置、部署、回滚或回归影响；经核实没有时写“无其他已知影响”>
```

四个标题必须按上述顺序各自独占一行，每段正文必须使用单独的 `- ...` 或 `* ...` 项目符号行。`--delivery-comment` 参数必须直接包含真实换行，不得把多行内容压成包含字面量 `\n` 或 `\r` 的单行字符串；预览中也必须按四段多行结构完整展示。

备注必须以已提交的仓库、文件、实际改动、已确认方案和交付资料为准，不得虚构或使用“功能优化”“完成需求”等空泛表述。`涉及模块`、`主要调整`、`验收口径` 不得为空或使用“无”占位；`其他影响` 经核实后允许明确写“无其他已知影响”。关联需求不存在、无法读取，任一分段不符合要求，或任务及需求中任一备注路径无法核实时，必须阻断禅道完成写入并请用户补充或修正。

使用相同内容生成完成预览：

```bash
node "${CODEX_HOME:-$HOME/.codex}/skills/zentao-task/scripts/zentao_task_workflow.js" \
  --task <任务ID> \
  --action complete \
  --real-started "<实际开始时间>" \
  --finished-date "<实际完成时间>" \
  --delivery-comment "<同时写入任务与需求的完整四段交付备注>"
```

1. 完整展示任务、归属需求 ID、每个动作、字段级当前值到目标值、任务与需求备注全文、工时计算、阻断项和完整 64 位哈希，并明确当前尚未更新禅道。
2. 预览计划必须明确“完成任务并新增任务备注”和“在归属需求下新增同内容备注”两个写入结果，并把任务完成、任务备注和需求备注共同纳入确认范围；不得仅预览任务状态更新。
3. 用户使用 `$zentao-task 确认` 后，从最近预览取得完整哈希，以完全相同参数追加：

   ```bash
   --apply --plan-hash <完整计划哈希>
   ```

4. 脚本只允许：
   - `wait`：先 `start`，回读成功后再 `finish`；
   - `doing`：保持远端实际开始时间一致后 `finish`；
   - 本次消耗 = 当前剩余，总消耗 = 原消耗 + 原剩余，完成后剩余 = 0。
5. 完成任务时必须通过 `finish` 动作同时新增任务备注；任务完成后回读任务操作记录，确认任务备注正文与预览一致，再使用已核实的需求备注写入路径新增同内容备注。随后回读需求操作记录，确认需求备注正文与预览一致，才视为阶段六成功。不得通过修改任务描述、需求描述、验收标准或需求状态来替代备注。
6. 哈希变化、状态不匹配、关联需求变化、任一备注内容不一致或任何部分失败时停止，报告真实远端状态，不直接重试。若任务已完成但任务或需求备注校验失败，必须明确报告部分完成状态，禁止重复执行任务完成操作。只有时间秒数按时间规则截断为 `00` 时自动接受并继续同步。
   - 只有远端状态已经是 `done` 或 `closed`，状态、工时、实际时间、完成者及其他业务字段均与计划一致，且唯一异常只是任务或需求备注无法精确回读时，才允许展示恢复选择：`1. 接受当前远端完成事实并继续最终指派选择`、`2. 接受当前远端完成事实但不指派并结束`、`3. 人工恢复后再回读`。
   - 选择 `1` 只接受已核实的远端完成字段，不代表备注已回读成功；不得重试任务完成或重复写入备注，不得应用 `zentao-completed` 阶段，必须保留并记录具体回读异常，然后进入阶段七重新生成独立的指派预览。
   - 选择 `2` 不再写禅道，不进入指派预览；保留并记录具体回读异常后结束交付。选择 `3` 等待人工处理，不自动重试写入或回读。
   - 状态、工时、实际时间、完成者、关联需求或其他业务字段存在任何非计划变化时，不得提供继续指派选项，只能报告真实状态并等待人工处理。
7. 任务完成、任务备注和需求备注均回读成功后，立即执行所属迭代的 `sync_zentao_project.js --execution <ID> --apply` 回读本地，再应用 `zentao-completed` 交付阶段。

## 阶段七：单独确认完成后指派

任务按标准路径完成并回读，或用户在阶段六的受控恢复路径中选择“接受当前远端完成事实并继续最终指派选择”后，生成指派预览：

```bash
node "${CODEX_HOME:-$HOME/.codex}/skills/zentao-task/scripts/zentao_task_workflow.js" \
  --task <任务ID> \
  --action assign \
  --assigned-to <本机项目上下文中的候选账号>
```

1. 从本机项目上下文读取候选账号，展示“当前账号 → 候选账号”和完整计划哈希，并提供：`1. 确认指派`、`2. 不指派并结束交付`；提示回复 `$zentao-task 1` 或 `$zentao-task 2`。本机未配置唯一候选人时必须询问，不得猜测。
2. 选择 `1` 后使用最近预览的完整哈希和完全相同参数追加 `--apply --plan-hash <哈希>`；选择 `2` 时不写禅道，保留当前指派人并记录决策。
3. 指派必须使用专用 `POST /api.php/v1/tasks/:id/assignto`，请求仅携带 `assignedTo` 和可选 `comment`，禁止使用通用 `update`。
4. 回读校验状态、工时、完成者、`realStarted`、`finishedDate` 和全部可编辑字段；只允许 `assignedTo` 按计划变化，`assignedDate`、`lastEditedBy`、`lastEditedDate` 可按禅道规则更新。
5. 若实际时间、状态、工时、完成者或业务字段发生非计划变化，立即停止并报告真实状态；不得误报成功或自动发起第二次指派。
6. 指派成功后再次同步所属迭代并应用 `assigned` 阶段；用户拒绝指派时交付仍可结束。通过受控恢复路径进入本阶段时，交付记录必须继续保留备注回读异常及用户接受远端完成事实的决策，不得补记 `zentao-completed` 或声称双备注已经核验成功。

## 汇报

- 预览：每个动作和字段的“当前值 → 目标值”、归属需求 ID、任务与需求的四段备注全文、完整哈希，并说明尚未写入。
- 完成：实际动作、任务状态、任务备注和需求备注的回读结果、工时、同步结果和是否等待指派确认。
- 指派：最终指派人、回读校验、同步结果；拒绝时明确未执行写操作。
