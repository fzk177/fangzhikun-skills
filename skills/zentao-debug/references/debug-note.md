# Obsidian Bug 排查记录

## 用途与边界

- 每次成功取得指定禅道 Bug 并完成排查后，留存一份本次分析记录。只读排查也要记录。本笔记是原始数据，工作日历只读取并加工展示，不承载原始记录。
- 此记录是排查快照，不是 Bug 交付记录；不能据此推断禅道状态、代码修复、测试或验收结果。
- 仅写本机 Obsidian，不写禅道、Git 或分支交付中心。不得复制密码、Token、Cookie、数据库凭据、敏感个人信息、整份原始日志或附件到 iCloud。
- 仅记录已核实事实。代码、日志、数据库结论应分别标注来源；证据不足的判断标记“待验证”。

## 文件位置与命名

在当前 Obsidian 仓库中创建：

```text
04.项目/00.Bug排查记录/Bug-<ID>-<排查日期YYYY-MM-DD>-<本次会话ID前8位>.md
```

排查日期使用实际分析当天的上海日期，不使用禅道创建、编辑或评论时间代替。若无法取得会话 ID，使用本次记录的上海时间 `HHmmss` 作为末段。再次排查同一 Bug 时创建新的记录；若同一次会话已存在同名记录，先检查内容，只补充本次新证据，保留人工修改，不覆盖旧结论。不要移动已有 Bug 交付记录。

## 元数据

Frontmatter 使用下列字段。`title` 必须使用禅道 Bug 原标题；不得用“历史排查”等占位语替代，标题未取得时应先补取只读摘要。字符串用 YAML 双引号保存，动态文本需正确转义引号和换行。其他未知值用空字符串，不猜测。`investigatedOn` 和 `investigatedAt` 必填，供工作日历按排查时间展示；`zentaoCreatedAt` 仅表示禅道创建时间。

```yaml
---
type: "zentao-bug-debug"
title: "<禅道 Bug 标题>"
zentaoBugId: "<纯数字 ID>"
zentaoStatus: "<读取时的禅道状态>"
severity: "<读取时的严重程度>"
project: "<已核实的项目名称或禅道 Bug>"
projectId: "<已核实的 Project Manager 项目 ID 或空>"
environment: "<已核实的故障环境或空>"
zentaoCreatedAt: "<禅道创建时间或空>"
investigatedOn: "<YYYY-MM-DD>"
investigatedAt: "<YYYY-MM-DDTHH:mm:ss+08:00>"
sessionId: "<当前 Codex 会话 ID 或空>"
symptom: "<一句话描述现象；未知则留空>"
conclusion: "<有证据支持的结论，未确定则写待验证>"
nextStep: "<建议动作或待验证事项>"
---
```

工作日历的“Bug”页签读取这些字段；卡片可打开完整笔记。`projectId` 仅在能核实与 Project Manager 项目一致时填写，以支持项目筛选。不要从标题猜项目。

## 正文结构

```markdown
# Bug #<ID> · <标题>

## 禅道事实快照

- 状态、严重程度、所属项目、指派、创建时间及本次读取时间。缺少的字段省略。
- 关键重现步骤、预期与实际结果；必要时引用附件名称或安全的 Obsidian 链接。

## 本次排查

- 环境与实际查询范围。
- 代码、日志、数据库证据及文件行号；未查询的来源不写成已查询。
- 根因或按可能性排列的待验证假设、反证、修复建议与风险。

## 后续动作

- 建议回归点或待验证项。只有真实执行后才写“已验证”“已修复”。

## 关联

- 本次 Codex 会话 ID；会话笔记路径已经存在时才添加 Wiki-link。
- Bug 交付记录已经存在时才添加 Wiki-link，不能因此改变交付状态。
```

写入后核对文件的 Frontmatter、日期、Bug ID 与关键事实；向用户报告 Obsidian 路径。若排查中断且未形成结论，可在已经成功取得禅道材料的前提下记录事实快照，并把结论标成“待验证”。
