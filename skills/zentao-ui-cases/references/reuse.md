# 复用与代码分层

## 先比较语义

每个验收点按以下信息检索并比较候选：业务实体与动作、角色与权限、输入约束、进入状态、产出状态、可观察判据、数据隔离与清理方式、环境限制和最近证据。

优先级是适用的成熟组合 → 已验证能力 → 已有页面对象/fixtures → 参数化或小幅扩展 → 新增。候选、待复核资产可作实现参考，不能继承“已验证”结论。同名不等于同义；成熟资产也可能不适用于新角色或新状态。

参数化适用于同一行为的不同数据和明确变体。不要增加大量模式开关，把多个业务职责塞入一个“通用”函数；扩展公共能力时复查现有调用者。跨项目复用只提取已证实共用的能力，项目认证和业务模型仍留在本项目。

## 四层职责

| 位置 | 作用 | 约束 |
| --- | --- | --- |
| `pages/`、按需 `components/` | 定位与页面基础操作 | 定位器集中管理，业务流程不重复复制定位器 |
| `cases/` | 原子业务能力 | 一个职责，例如创建草稿；显式参数、返回业务 ID/状态，不用全局变量藏输入输出 |
| `flows/` | 原子能力和已有流程的有序组合 | 明确前后置条件；无循环依赖，不直接调用 pytest `test_*` |
| `tests/` | 单一业务行为和验收判定 | 每个测试可单独运行，失败不导致后续测试因共享状态连锁失败 |

这是新增能力的推荐位置，不要求重构已经合理的项目结构。目录缺失时按需创建；可导入的新增 Python 子包遵循当前项目的安装方式。

原子能力可以包含保证自身契约的局部检查，例如“创建成功并返回草稿 ID”；测试负责验收预期。测试的“单一职责”不等于只允许一条断言，围绕同一行为可验证多个相关结果。

示意：`create_draft(data) -> draft_id`、`submit_draft(draft_id)` 和 `assert_status(draft_id, expected)` 可组成提交流程；测试准备独立数据后调用流程，验证角色与状态规则。名称仅为说明，不代表已存在业务资产。

## 独立执行和业务数据

- 不让测试 B 读取测试 A 创建的固定对象，也不按文件顺序串行完成一条业务链。链路放在单个场景的流程中，由各测试自行准备前置条件。
- fixtures 管理登录、数据准备和清理。账号/租户/数据的共享范围要显式，浏览器上下文隔离不代表后端业务数据隔离。
- 创建数据使用唯一标识并回收；使用 `yield`/`finally` 清理，记录无法清理的资源。重试前核对已有副作用，不能重复提交付款、审批等动作。
- 若测试目标不是登录 UI，可复用已授权登录态；登录行为自身仍用独立 UI 测试。允许 API 准备数据时记录方式，不把 API 操作伪装成 UI 覆盖。
- 复用同一用户会话时核实角色、租户、有效期和目标环境；认证状态与密码只留在忽略目录/受控环境变量，不进入登记或 Story 说明。

## 定位器与真实判定

优先项目已有稳定的 role、label、test id。避免依赖顺序的 `nth()`、长 XPath 和固定 sleep；需要业务消歧时通过容器、实体 ID 或明确文本缩小范围。没有定位证据时记录待运行时确认，不自动修改前端来加 test id。

使用可观察的业务结果作为判据，例如列表中目标实体的最终状态；仅检查按钮被点击、接口返回 200 或弹窗关闭通常不足以覆盖业务验收。异步变化使用有界条件等待；不能吞掉异常、宽泛捕获后继续通过，或遇失败直接删除断言。

需求要求但前端未实现的规则保留为差异和待处理项。可以生成有明确预期的待运行测试，不能将实现的错误行为写成期望值；需求确实含糊时先澄清对应规则，继续处理其他 AC。
