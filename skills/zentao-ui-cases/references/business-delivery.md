# 业务交付与自动化关联

默认面向用户的入口只有业务用例 CSV 和关联页，技术附件保持已有路径，避免破坏历史链接。单份 `test-cases.json` 是维护源，不从 CSV、HTML 和代码分别维护三套用例。

## 先写能读懂、能执行的业务用例

- 一条用例表达一个可判定的业务场景，写明角色、进入状态、数据及限制、可操作步骤和独立预期。前置数据的设计别名与实际创建记录分开，不把编造的订单号写成已存在数据。
- `title/preconditions/steps/expected` 使用业务语言。技术定位器、内部权限键、fixture、版本核验、Trace要求及脚本引用放其他技术字段。最终预期可覆盖多个步骤，不按数组下标强行将步骤与预期一一配对，也不能补造每步预期。
- 先覆盖需求要求的业务范围，再分配 `ai/ai_review/human`，标出待实现或阻塞。人工、服务端、历史数据和运维核验不会因已有UI脚本而从业务CSV消失。
- 可复用登录、选类型、填表等流程不等于已有完整业务覆盖；判定仍由具体测试中的断言负责。只验证未保存表单的用例，前置、预期与关联页都必须明确边界，不能称为保存、审批或历史修正已验证。

## 业务覆盖与实现状态分别展示

新计划展示design_model的范围、模型内覆盖项去向、关联用例及原因；实现、数据准备、判据就绪和执行结果分别保存。规则或消费者未决项不能用某个UI子场景通过关闭。历史无模型材料明确标为覆盖未审查。业务覆盖详情见[test-design.md](test-design.md)，不新增CSV列。

## CSV 与参考样例的对应

列名与顺序固定：所属模块、用例名称、前置条件、步骤、预期、关键词、优先级、用例类型、适用阶段、相关研发需求、类型可选值列表、阶段可选值列表。

UTF-8 BOM、标准CSV引号及多行单元格；步骤和最终预期各自编号，不要求数量相同。关键词包含 `用例ID:<稳定ID>` 和 AC，需求列使用 `(#<Story ID>)`。不额外增加自动化状态、脚本或数据库字段，不伪造禅道用例ID。实际导入得到的禅道用例ID可随后独立登记，不能依赖标题作为关联键。当前仅生成导入文件，不访问或写入禅道。

导入默认字段放清单顶层 `zentao_export`，每条用例可用 `zentao` 覆盖：

```json
{
  "zentao_export": {
    "module": "/真实模块路径(#实际模块ID)",
    "priority": "2",
    "case_type": "功能测试",
    "stage": "系统测试阶段"
  }
}
```

这是字段示意，必须替换真实模块。优先级1–4必须来自用户确认的用例优先级约定，可设置经过确认的默认值并在单条覆盖；不从风险等级机械换算。`case_type/stage` 默认沿用参考模板的“功能测试/系统测试阶段”，人工项未配置类型时为“其他”；项目枚举不同则调整配置。末尾两列保留为空。

缺少模块或导入优先级时生成 `05-business-test-cases-draft.csv`，关联页明确待补项；齐备后文件名为 `05-business-test-cases.csv`。字段齐备仅表示本地结构通过，不表示禅道导入已实测。公式前缀字段会被拒绝，需改成明确业务文本，不能静默改写测试内容。

## 用例、脚本、流程及断言

现有 `python_refs` 指向具体测试函数/方法及参数场景，`asset_ids` 指向登记的流程与原子能力；参数场景ID不等于完整运行node ID。支持 `path.py::Class.method[场景ID]` 和 pytest 的 `path.py::Class::method[场景ID]`。

新增或修改自动化时补充可选 `automation`，旧清单保持兼容：

```json
{
  "automation": {
    "state": "implemented",
    "reason": "已实现本条未保存表单的业务判定",
    "steps": [
      {
        "step": 2,
        "asset_ids": ["实际已登记的流程ID"],
        "code_refs": ["projects/实际项目/tests/test_example.py::_assert_result"],
        "expected_indexes": [1]
      }
    ]
  }
}
```

该示意不能直接登记为真实资产。`state` 为 `implemented/planned/blocked/manual`；待实现或实现受阻须有原因，`manual` 仅用于独立人工项。未填写时，存在测试引用仅显示“已有测试入口”，不自动宣称整条已实现或已验证。`ai_review` 保持独立人工复核链接。

`step` 为业务步骤1起序号；`code_refs` 可指向测试、fixture、页面函数或独立断言函数；`expected_indexes` 指向本用例最终预期，动作步骤可不绑定预期。映射前必须读真实调用者、参数、流程依赖顺序及判定代码；不能用函数名相似或资产平铺列表推断调用关系。一个用例可以关联多个测试入口，共享流程也可以服务多个用例；若拆成多个独立场景，保持独立用例ID和各自覆盖边界。

没有步骤关联时页面明确“尚未登记”，不伪造流程图。语义审阅与自动校验分别记录。历史生成文件不要求为填满表格而整批重写；只在相关需求或能力更新时增量补齐。

## 校验与运行结果

`plan/view/report` 传 `--repo` 后，只用AST、源码哈希和登记读取核验：代码路径位于仓库内、函数/方法存在、显式静态参数ID及数据、资产ID、依赖引用和无环、相关资产源码哈希、步骤与预期索引。源码和测试不被导入，不调用pytest收集。参数由动态表达式构造、暂无法静态解析时明确待核验，不能算已验证。JSON风格catalog不需依赖；实际YAML需当前Python已有PyYAML，缺失则明确失败，不静默安装。

不传 `--repo` 保留旧调用兼容，但主页面显示代码引用未核验，不能把该输出计为关联检查通过。登记是声明，静态通过不证明实际调用顺序、断言充分性或业务已通过。

执行结果必须经原有证据门槛与清单SHA256校验。存在真实 `node_id` 时，核对声明测试入口及参数场景；记录了实际pytest参数时核对静态参数值。没有记录入口就标为缺口，不反向编造。多入口或动态参数需人工按真实运行证据核对，不能把一个子场景通过当整条通过。

关联页将实现状态和执行状态分别显示，包含未执行、选定范围外、失败、阻塞及待人工核验。载入历史运行时标明时间、环境、账号角色和版本报告链接，不声称本次重新运行。阻塞在前置步骤时不能将后续关联流程记为本次已调用；过期的规划缺口不得覆盖匹配哈希的实际运行事实。

CSV/关联页是派生产物。用户手工修改CSV后，先识别稳定ID、保留原快照、与清单比对并明确接受哪些业务变更，再更新清单及代码；不能静默双向覆盖或直接沿用旧运行结果。变更后的清单使用新快照，旧执行证据仍绑定原哈希。
