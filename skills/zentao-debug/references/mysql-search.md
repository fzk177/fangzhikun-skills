# Bug 分析中的数据库证据补全

显式调用 `$zentao-debug` 后，满足本参考条件时可以直接把 `$mysql-search` 作为内部只读子流程使用，用户不需要再次单独输入 `$mysql-search`。

## 何时查询

先完成禅道材料梳理和初步代码调用链分析。只有数据库事实能回答一个明确问题时才查询，例如：

- 验证 Bug 涉及的业务单号、状态、软删除标记、关联记录或重复数据是否真实存在。
- 核对代码分支依赖的枚举值、字典值、NULL/空串或时间边界。
- 判断异常来自单条脏数据、关联缺失、重复业务键还是代码逻辑。
- 日志或禅道描述提供了具体业务编号，需要核对目标环境的当前数据状态。

以下情况不要查询：

- 禅道和代码事实已经足以确认根因，数据库结果不会区分现有假设。
- 缺少环境且不能从用户请求或 Bug 正文唯一确定。
- 只有宽泛业务描述，尚未从代码确认表、字段和枚举映射。
- 需要写入、修数、DDL、锁定、调用存储过程或修改权限；这些不属于 `$mysql-search`。

## 执行规则

1. 完整读取 [$mysql-search](../../mysql-search/SKILL.md)，遵守它的环境路由、只读 SQL、凭据托管、结果限制和脱敏要求。
2. 从 Bug、用户请求和代码调用链提取环境、schema、表、业务编号、字段与待验证假设；schema 在每次查询时通过 `--database` 明确传入，不要把整段 Bug 正文直接转换成 SQL。
3. 先通过 Mapper、Query、枚举和必要的 `DESC` 确认表字段和值，再执行有明确过滤条件的最小 `SELECT`。
4. 只使用 `$mysql-search` 的 `scripts/query.sh`，不得读取 `application-*.yml` 中的账号密码或自行拼接数据库命令。
5. 配置、钥匙串、CLI 或网络不可用时，只说明阻塞点并引导用户按 `$mysql-search/references/setup.md` 一次性配置；不得在 Bug 材料或对话中索要密码。
6. 临时查询结果放在 `mktemp -d` 目录，只保留支撑结论的最小脱敏片段，不生成项目内 SQL、JSON、CSV 或其他长期文件。

## 合并证据

- 明确写出环境、数据库、表、查询目的和主要条件。
- 将“数据库事实”与禅道描述、代码事实、日志事实和推测分开标注。
- 空结果先核对环境、schema、软删除、枚举编码、大小写和时间范围，只能说明当前条件未命中。
- 数据库当前状态不必然等于 Bug 发生时状态；涉及时序变化时结合日志或历史证据，并说明限制。
- 输出前脱敏，只展示定位根因所需的字段和少量记录。
