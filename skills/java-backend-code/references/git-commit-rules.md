# Git 提交规范

## 适用范围

在 Java 后端编码任务中起草、检查提交说明，或执行已获授权的提交时使用。本规范不扩大代码修改、测试、Git、禅道或发布操作的授权范围；`test`、`docs`、`style`、`revert` 等类型本身不构成执行相应修改的许可。

## 提交格式

```text
类型(模块): 具体描述 task#编号
类型(模块): 具体描述 story#编号
类型(模块): 具体描述 bug#编号
类型(模块): 具体描述 no-ticket
```

- 类型使用小写英文；模块、描述及正文说明使用中文，必要技术标识保留英文。
- 模块必填，使用英文括号、冒号；冒号后及关联标记前各保留一个空格。
- 标题末尾只填写一个主要关联标记；编号必须为真实且相关的正整数，其他关联写入正文。完成禅道任务的提交还须满足下文“任务提交必须同时关联需求”的要求。
- `task#编号` 对应禅道任务，`story#编号` 对应禅道需求，`bug#编号` 对应禅道 Bug。同一任务或需求可以对应多次提交。
- 不兼容变更使用 `类型(模块)!: 具体描述 关联标记`，正文增加 `BREAKING CHANGE: 中文说明`，明确不兼容点及迁移方式。

## 类型选择

| 类型 | 使用场景 |
|---|---|
| `feat` | 新功能或已确认的业务规则调整 |
| `fix` | 普通缺陷修复 |
| `hotfix` | 生产紧急修复，团队自定义类型 |
| `refactor` | 重构，保持业务行为一致 |
| `perf` | 性能优化 |
| `docs` | 仅修改文档 |
| `test` | 仅修改测试 |
| `style` | 仅调整代码格式 |
| `build` | 构建、打包或依赖调整 |
| `ci` | 流水线及自动检查、发布流程调整 |
| `chore` | 开发工具、仓库配置等日常维护 |
| `revert` | 回退已有变更，正文注明原 commit SHA 和原因 |

按实际改动选择类型。页面样式及交互调整按目的使用 `feat` 或 `fix`；与功能一起提交的必要文档和测试跟随主要类型。分类规则不扩大本 Skill 的 Java 后端修改范围。

## 禅道关联与 no-ticket

- `feat` 优先关联具体的 `task#编号`，没有对应任务时可关联 `story#编号`；`fix`、`hotfix` 默认关联 `bug#编号`，已拆为修复任务时也可关联 `task#编号`；其他类型关联对应任务、需求或 Bug。
- 已有需求编号但尚未拆分任务时，可直接使用 `story#编号`，无需仅为提交代码而创建任务或改用 `no-ticket`。
- **任务提交必须同时关联需求**：完成禅道任务的提交，标题以 `task#任务编号` 作为主要关联标记，正文第一行写 `关联需求：story#需求编号。`，两者缺一不可。需求编号从当前任务上下文获取；上下文没有时必须查询禅道任务的所属需求（`story` 字段）后填写，不得猜测或省略。查询失败或任务确实未关联需求时停止提交准备并告知用户，由用户确认处理方式。
- 所有类型，包括 `feat`，确实没有对应编号时均可使用 `no-ticket`，正文必须填写具体的“无单号原因”。已有编号时使用真实关联，禁止编造或挂靠不相关编号。
- 未核实是否存在关联编号时，不能直接认定为无单号。结合任务上下文或可用的查询结果核对；无法核实时明确说明，不声称已验证真实性。
- 正式业务功能、普通缺陷在合入发布分支前补齐禅道关联；原型、实验及内部工具由评审人确认是否需要补登记。
- 紧急修复使用 `no-ticket` 时，写明补登记负责人和期限，默认上线后一个工作日内补登记；负责人和期限不能编造，缺失时请用户补充。
- 补登记后在禅道和合并请求中关联编号及 commit SHA，保留已共享、合入或发布的提交历史，不为补编号而改写这些历史。
- 上述补登记及关联操作仍需对应操作授权；不因本规范要求而自动创建禅道单据、修改状态或编辑合并请求。

## 提交前检查

- 检查暂存区实际改动，按独立功能或修复点原子提交，无关改动分开提交。发现暂存区存在本次范围外或归属不明的改动时，先厘清范围，不直接纳入本次提交。
- 使用明确业务模块和具体动作，避免仅写“更新”“修改代码”“优化”。
- 涉及数据库、接口兼容或发布操作时，正文说明影响、迁移或回滚办法及实际验证结果；不适用的内容说明理由，不编造已执行操作。
- 验证结果如实区分静态复核、构建、测试或其他已完成检查。仅做静态复核时明确写明；不得为填写验证结果而绕过 Skill 的测试确认要求。
- 核对类型、格式、关联标记及必要正文。团队规则由 Codeup 正则检查格式，禅道关联真实性和例外理由由查询或评审核实；未读取实际配置或结果时，不宣称 Codeup 已通过检查。
- 格式检查通过不等于已经完成提交，也不替代关联真实性、变更范围及操作授权检查。

## 示例

以下编号仅展示格式，实际提交使用对应的真实编号。

```text
feat(航次订立): 新增多船东业务类型 story#807
fix(付款): 修复支付结果重复处理 bug#12345
```

完成禅道任务时，标题关联任务、正文第一行关联需求：

```text
feat(航次订立): 新增多船东业务类型 task#1475

关联需求：story#807。
```

```text
feat(开发工具): 新增本地接口调试页面 no-ticket

无单号原因：内部开发辅助工具，当前未在禅道登记。
```

不兼容变更的格式示意，实际填写时替换为真实信息：

```text
feat(业务模块)!: 具体变更描述 task#真实编号

BREAKING CHANGE: 说明不兼容点及迁移方式。
影响范围：填写实际影响的接口或调用方。
回滚办法：填写实际可行的回滚办法，或说明不适用的原因。
验证结果：填写实际执行的检查及结果。
```
