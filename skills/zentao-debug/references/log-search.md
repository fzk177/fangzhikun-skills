# Bug 分析中的日志证据补全

显式调用 `$zentao-debug` 后，满足本参考条件时可以直接把 `$log-search` 作为内部只读子流程使用，用户不需要再次单独输入 `$log-search`。

## 何时查询

先完成禅道材料梳理和初步代码调用链分析。只有日志能回答一个明确问题，并且至少符合以下一种情况时才查询：

- 需要确认线上实际抛出的首个异常、最深层 `Caused by` 或下游响应。
- 同一代码路径存在多个运行时分支，需要用请求参数、业务编号或调用顺序区分。
- 问题具有偶发、环境相关或时序相关特征，静态代码无法独立复现或证明。
- 禅道描述与代码行为矛盾，需要运行时证据判断实际进入的版本或分支。
- 修复方案依赖影响范围，需要确认同类错误是否在目标时间窗口重复出现。

以下情况不要查询：

- 现有禅道、代码或只读数据库证据已经足以确认根因。
- 只是因为日志工具可用，但没有待验证问题。
- 只能使用宽泛关键词做大范围、跨环境或全天扫描。
- 查询目的实际是查看服务状态、配置或执行服务器运维；这不属于 `$log-search`。

## 查询前置条件

从 Bug 正文、历史、附件和用户请求中提取以下信息，已有内容不要重复询问：

- 环境：`dev`、`pre` 或 `prod/生产`。
- 事件时间或可信时间范围，统一按 `Asia/Shanghai` 解释。
- 至少一个稳定线索：traceId、requestId、业务单号、接口路径、异常类、错误短语或其他具有选择性的关键词。
- 应用或业务域，尤其是 pre 环境。

禅道创建时间、最后编辑时间和评论时间不能自动当作故障发生时间，除非正文或历史明确说明二者一致。缺少环境或时间且无法唯一推导时，只有在日志证据对结论确实必要的情况下才询问用户；否则继续完成代码分析，并把日志证据标为缺失。

## 执行规则

1. 完整读取 [$log-search](../../log-search/SKILL.md)，继续遵守它的只读边界、时间窗口、环境路由、查询脚本和脱敏要求。
2. 把从 Bug 中提取的环境、北京时间范围、应用和稳定线索作为查询输入，不把整段 Bug 正文、附件内容或异常堆栈直接作为搜索词。
3. 先用选择性最高的标识精确查询。命中后只围绕同一 trace、request 或业务编号扩展上下文。
4. 日志无结果时依次核对环境、时间、字段名、应用和轮转情况；不要直接扩大为无边界查询。
5. 临时日志结果与禅道材料一样放在 `mktemp -d` 目录，只保留支撑结论的最小片段，不写入项目目录或长期文件。
6. SSH、SLS 认证或工具不可用时，只说明阻塞点。不得在 `$zentao-debug` 中安装工具、修改 SSH 配置、写入凭据或转为服务器运维操作。

## 合并证据

将日志证据并入 Bug 分析时：

- 明确写出环境、应用或 Logstore、北京时间起止范围和主要查询条件。
- 按时间顺序展示已脱敏的最小关键片段，并注明来源。
- 分开标记禅道描述、代码事实和日志事实，说明它们如何共同支持或否定某个假设。
- 不得仅根据单条 `ERROR` 下结论；优先定位首个业务失败、最深层原因及后续包装异常。
- 日志与 Bug 描述冲突时如实呈现，不为了匹配预设结论而忽略反证。
- 查询不到日志不能证明问题未发生，应说明日志留存、采样、时间偏差或跨服务链路中断等限制。
